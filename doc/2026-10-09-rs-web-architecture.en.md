# rs-web architecture overview

> Date: 2026-10-09. This document describes the current `qubit-web` 0.3.0 module layout. See the [lifecycle and resource boundary summary](2026-10-09-rs-web-lifecycle-design.en.md) for shutdown and session contracts, and the [English user guide](user_guide.md) for integration steps. The [2026-10-08 design record](2026-10-08-rs-web-design.md) is historical.

## Current API and operational notes

Native Axum construction uses `RequestLimitLayer::new(limits)` and `StreamAdmissionLayer::new(limits)` or `StreamAdmissionLayer::from_state(state)` without Router-state type parameters. Existing calls that explicitly supplied those turbofish type arguments must remove them. `WsSession::close()` is idempotent and can be retried after cancelling its future; `recv()` returns `None` after close. Unmatched-route diagnostics use only `<unmatched>`. Zero or unrepresentable request-header and SSE keep-alive durations are rejected as `InvalidConfig`.

## Request path and module map

`WebServer` owns the bound TCP listener, per-server transport policy, and shared `ServerContext`. It accepts and caps transport connections, optionally performs TLS negotiation, and adapts each stream into Hyper with upgrade support. Hyper dispatches requests through the application's Axum `Router<()>`.

Accept retries transient socket I/O errors at most eight times consecutively, with delays of 10, 20, 40, 80, 160, 320, 640, and 1,000 ms (2.27 seconds total). The ninth consecutive error terminates serving; a successful accept resets the count. `InvalidInput`, `PermissionDenied`, `Unsupported`, and `NotConnected` terminate immediately. Shutdown and connection-task completion can interrupt a delay; rebuilding the accept future retains the absolute retry deadline. On terminal failure the listener is dropped, managed sessions are cancelled, and connection tasks are given the graceful shutdown deadline before remaining tasks are aborted and reaped. `WebServerError::ServeFailed` retains the final I/O error as its source.

Applications can construct that router directly or use `ControllerRoutes` with the controller macros. Distinct Controller types with the same terminal type name can both use `rest_controller` and be assembled in one module. `ControllerRoutes::add` incrementally reuses its route matcher while preflighting complete route templates, then returns `ControllerRouteError` for duplicate method/path declarations, invalid paths, and matching-template conflicts before registration. This changes assembly cost only: error classification, complete preflight before registration, and route behavior remain unchanged. `finish()` returns the Axum `Router` directly. Later merges with native Axum routers retain Axum's own conflict behavior. Controller `short` routes receive the builder's default request budget; Controller `sse`/`ws` routes use the builder's separate stream-admission state. Native Axum branches receive neither policy unless the application installs the appropriate layer. Limits are scoped to those routes and are not a server-wide policy. `DiagnosticLayer::new()` retains response-header-only logging. Applications that explicitly install `DiagnosticLayer::with_body_diagnostics()` also receive one allowlisted `response_body_end` event (`complete`, `timeout`, `body_error`, or `dropped`) when the response body terminates; the layer should sit outside `RequestLimitLayer` to observe its timeout. A dropped body is not proof of client disconnect, and completion is not proof of network delivery. Neither event includes payload or error text.

The main module responsibilities are:

| Module | Responsibility |
| --- | --- |
| `server` | Bind HTTP/HTTPS listeners, run the Axum router, cap transport connections, coordinate shutdown, and report shutdown results. |
| `mvc` | Assemble controller routes, reject duplicate methods and conflicting route templates before registration, and expose route metadata. |
| `limit` | Provide body, concurrency, and time budgets for short requests and stream admission. Controller routes receive defaults in two separate state domains; native Axum branches opt in by installing the appropriate layer. |
| `json` | Enforce strict JSON input/output byte and structural limits when the `json` feature is enabled. |
| `sse` | Admit bounded server-sent event streams and track them as managed sessions. |
| `ws` | Validate WebSocket policy and Origin, reserve capacity, and manage inbound/outbound session I/O when the `ws` feature is enabled. |
| `config` | Parse explicit configuration values into listener options and separate HTTP route limits when the `config` feature is enabled. |
| `tls` | Load or wrap rustls configuration for HTTPS when `tls` is enabled. |
| `diagnostic`, `error`, `route_kind` | Supply request diagnostics, stable public errors, and shared route classification. |

## Capacity domains and defaults

Each limit protects a specific resource. Its configured count must not be read as a single service-wide concurrency ceiling.

| Domain | Default | Scope and overload behavior |
| --- | --- | --- |
| Accepted transport connections | 1,024 per `WebServer` | Configured values must be within `1..=tokio::sync::Semaphore::MAX_PERMITS`. Includes TLS handshakes and HTTP connection futures. When full, the accept loop stops accepting; clients may wait in the OS backlog or fail to connect. No HTTP 503 is generated. |
| Concurrent HTTP/2 streams | 200 per connection | Set with `ServerOptions::with_http2_max_concurrent_streams` or `transport.http2_max_concurrent_streams` (`1..=u32::MAX`) with `config`. This is a protocol-level per-connection limit, independent of transport connection, route, and session caps; it is not a process-wide request, header-byte, or memory budget. |
| HTTP header buffering | Hyper defaults unless configured | Optional `http1_max_buffer_bytes` (at least 8,192 bytes) limits HTTP/1 parser buffering, not exact header-list bytes. Optional `http2_max_header_list_bytes` (positive `u32`) limits decoded HTTP/2 header-list size. With `config`, use `transport.http1_max_buffer_bytes` and `transport.http2_max_header_list_bytes`; omission preserves Hyper defaults. These are distinct protocol budgets, not total process-memory limits. |
| Controller short requests | 256 in flight per `ControllerRoutes` builder | Configured values must be within `1..=tokio::sync::Semaphore::MAX_PERMITS`. `ControllerRoutes::new()` applies `HttpLimits::default()`: 1 MiB per body and a 30-second handler/response-body deadline as well. On expiry, the application body and short-request permit are released without waiting for another body poll. After headers are sent, timeout can only appear as a body error when the transport polls again; it does not close the connection. `with_http_limits` replaces these defaults and should be called before adding controllers. Each builder has its own shared state. Native Axum branches require an explicit `RequestLimitLayer`; `WebServer` does not install route limits. Full capacity returns a capacity rejection. |
| SSE connections | 128 per `SseConnectionPolicy` by default | `new`/`default` policies create independent capacity domains; clones share their domain. Exhaustion is reported separately from shutdown rejection. |
| WebSocket connections | 128 per `WsUpgradePolicy` by default | `new`/`default` policies create independent capacity domains; clones share their domain. Policy validation uses final field values; `max_connections` must be within `1..=tokio::sync::Semaphore::MAX_PERMITS`, with zero reported as `WsPolicyError::ZeroLimit` and larger values as `WsPolicyError::ConnectionLimitTooLarge`. `inbound_queue_limits` accepts 1 through `Semaphore::MAX_PERMITS` messages and a positive byte budget; an oversized message count returns `WsPolicyError::InboundQueueLimitTooLarge`. Callers exhaustively matching `WsPolicyError` should handle this new variant. Failed admission produces a rejection before the session is managed. |
| Managed server sessions | No independent numeric cap | `ServerContext` tracks admitted SSE and WebSocket sessions for shutdown accounting. It is not a global connection limit and does not include ordinary requests, native Axum upgrades, or application background jobs. |

To share an SSE or WebSocket capacity across routes, create one policy at application startup, put it in application state, and pass its clones to handlers. Multiple separately created policies multiply the effective aggregate capacity. The same planning principle applies to short-request branches: configure and share the intended branch state explicitly.

## Request budgets and long-lived streams

Long-lived Controller `sse` and `ws` routes use a `StreamAdmissionState` separate from the short-request `LimitState`. Defaults per stream-admission state are 1 MiB buffered per request, 256 concurrent admissions, and 10 seconds through handler response headers. The theoretical body-buffer budget is 256 MiB per state domain plus request/runtime overhead. `with_stream_admission_limits` replaces the Controller builder's stream budget for routes added afterward. Native Axum SSE/WS branches must explicitly install `StreamAdmissionLayer`; use `StreamAdmissionState` and `from_state` to share capacity across branches. A fresh layer creates an independent state domain. Oversize/read failure/capacity exhaustion/admission timeout return 413 `body_too_large`, 400 `body_read_failed`, 503 `capacity_exceeded`, and 504 `request_timeout`, respectively. If the absolute deadline cannot be represented at runtime, the layer returns HTTP 500 `invalid_configuration`. The deadline ends at response headers; it does not cover SSE response streaming or a WebSocket session.

`HttpLimits::default()` allows 1 MiB per request body, 256 concurrent in-flight short requests, and 30 seconds for handler work plus response-body streaming. `ControllerRoutes::new()` applies this policy to Controller `short` routes by default; `with_http_limits` replaces it for routes added afterward. Controller `sse` and `ws` routes use stream admission rather than the short-request layer. Native Axum branches require an explicit `RequestLimitLayer`, because `WebServer` serves the Router as supplied and does not add route limits. The request body is counted as the selected route consumes it; the middleware does not drain an otherwise unread body just to enforce the budget. Capacity exhaustion, an oversized body, and a request deadline have stable rejection outcomes. Unrepresentable absolute request deadlines are rejected as `WebServerError::InvalidConfig`; an extreme runtime deadline failure returns HTTP 500 with code `invalid_configuration`. Ordinary handler timeouts remain `504 Gateway Timeout`. If a deadline expires after response headers are sent, the application body is dropped and the short-request permit is released at expiry; the status cannot change. With body diagnostics enabled, the timeout event is emitted when the deadline fires even if the transport never polls the response body again; the body error itself is still observed only on a later poll. Without that opt-in observer, existing logging behavior is unchanged. Transport backpressure can delay when a client observes this error. The deadline does not close the TCP or HTTP/2 connection, which is governed by the independent transport policy.

When enabled, `JsonLimits::default()` independently bounds input and output payloads to 1 MiB, nesting depth to 64, value nodes to 100,000, array items and object entries to 10,000 each, key bytes to 16 KiB, string bytes to 256 KiB, and number bytes to 128. JSON limits are separate from the generic HTTP body budget; configure compatible values when both apply.

At the input stage, `BoundedJson` rejects an oversized body or decode budget through `JsonRejection::BudgetExceeded` (`413`); malformed JSON and unsupported media types have distinct extractor rejections. At the output stage, `json_response` encodes the complete response before returning it and reports output-budget or serialization failures as `JsonResponseError` (`json_output_budget_exceeded` or `json_encode_failed`). The application must handle extractor rejections and the returned response-encoding error; the library does not choose an application-specific fallback response.

SSE and WebSocket routes are long-lived and must not be put behind short-request concurrency/deadline middleware. SSE keep-alives and WebSocket frame/message/queue limits belong to their respective policy modules. WebSocket inbound defaults are 64 queued messages and 1 MiB aggregate payload per connection, configured separately from outbound `queue_limits` through `inbound_queue_limits`. At most one additional pending message is charged to that byte budget. With 128 default connections, this bounds queued and pending payloads to about 128 MiB, plus one possible 1 MiB protocol-reassembled message per connection, allocation overhead, and application-owned memory. The [lifecycle summary](2026-10-09-rs-web-lifecycle-design.en.md) documents session shutdown, queue closure, inbound backpressure, and Origin behavior.

## Timeouts, shutdown, and configuration

`ServerOptions` defaults to 200 concurrent HTTP/2 streams per connection, a 10-second HTTP/1 header and TLS handshake timeout, a 30-second idle transport timeout, and a 30-second graceful shutdown deadline. Optional HTTP/1 parser-buffer and HTTP/2 decoded header-list budgets preserve Hyper defaults unless explicitly set. The HTTP/1 header timeout is not an HTTP/2 header-block deadline. The WEB-004 protocol experiment found SSE continued while a second stream's valid header block was incomplete; the separate resource investigation records whether the tested bounded cases showed retained resources and recovery. See the [investigation report](http2-resource-investigation-20261103.md) for the versioned source review and evidence. The idle timeout closes a TCP/TLS connection only while no request handler or response body is active; it does not bound a stalled active request. Long-lived response bodies therefore pause transport-idle expiry.

On shutdown, the server stops accepting sockets, closes managed-session admission, signals active sessions, and waits for HTTP connection tasks and managed SSE/WS sessions against one absolute deadline. `ServerOptions` sets the timeout and `ServerContext` supplies the shared deadline to WebSocket sessions; `WsUpgradePolicy` has no separate shutdown timeout. Unrepresentable shutdown deadlines are rejected as `WebServerError::InvalidConfig`; an extreme runtime deadline failure cancels sessions and drains connection tasks before returning an error. `ShutdownReport::graceful` is true only if both groups finish in time. The report records unfinished managed sessions; it cannot claim arbitrary application background work has stopped. `WebServer` owns and tracks the connection tasks, while Hyper/hyper-util drives each connection. This implementation does not provide a provable count of forcibly closed connections, so `forced_connections` is `None`.

`ConfiguredWeb` parses an explicit configuration object. It returns `ServerOptions` separately from `HttpLimits`. Controller short routes already use `HttpLimits::default()`; pass the configured limits to `with_http_limits` to replace that policy. For native Axum routes, install `RequestLimitLayer` on selected short branches. `WebServer` does not modify the Router. With `config`, transport defaults are `transport.max_connections = 1024`, `transport.idle_timeout_ms = 30000`, and `transport.http2_max_concurrent_streams = 200` per HTTP/2 connection. Optional `transport.http1_max_buffer_bytes` and `transport.http2_max_header_list_bytes` preserve Hyper's defaults when omitted; explicit values must be at least 8192 and a positive `u32`, respectively. The stream setting also accepts a positive `u32`. HTTP policy keys include `http.max_body_bytes`, `http.max_concurrent_requests`, and `http.request_timeout_ms`. The two concurrency keys accept only `1..=tokio::sync::Semaphore::MAX_PERMITS`; invalid values identify their original key through `ConfigOptionsError::field()`. TLS is optional and configured separately through `TlsConfig`; PEM load failures are reduced to `TlsInvalid` without exposing key material or paths.

## Failure stages and application responsibilities

| Stage | Library behavior | Application responsibility |
| --- | --- | --- |
| Startup and bind | Validates options, binds the socket, queries its local address, and validates TLS configuration before serving. Public errors distinguish invalid configuration, bind/address failures, TLS errors, and serve/accept failures. | Supply a valid address and positive timeouts/capacity; load valid certificates and private keys; decide how startup errors are surfaced. |
| Route assembly | Detects duplicate controller method/path declarations. Request-policy middleware returns stable body-size, capacity, and timeout rejections on Controller short routes and on native branches where installed. | Assemble intended routes, replace Controller defaults when needed, install limits on appropriate native branches, and translate public rejections into application behavior where needed. |
| SSE admission | Reserves policy capacity and a managed server session before creating the stream. Capacity exhaustion and shutdown rejection are distinct. | Choose shared policy state; implement event IDs, replay, and event buffering; handle client reconnects. |
| WebSocket admission and I/O | Checks policy and Origin, rejects requests with repeated Origin fields before upgrade, reserves policy/server-session capacity, and manages reader/writer lifecycle. It bounds frames, messages, queues, and inbound delivery. | Authenticate before `on_upgrade`, configure allowed Origins, send at most one Origin field, keep calling `WsSession::recv()`, and handle application-level processing and delivery semantics. Origin is not authentication. |
| Shutdown | Uses one deadline for HTTP connections and managed sessions; reports remaining managed sessions. | Stop or supervise application background jobs and decide what to do when the report is not graceful. Native Axum upgrades and arbitrary jobs are outside managed-session accounting. |

The [lifecycle summary](2026-10-09-rs-web-lifecycle-design.en.md) is the concise reference for current session and shutdown guarantees; the [user guide](user_guide.md) covers concrete integration.

## Cooperative deadlines and transport peer

Request, stream-admission, and shutdown deadlines rely on Tokio scheduling and cooperative cancellation. Synchronous work that does not yield can delay timeout checks and cleanup, and may complete successfully after its deadline. Cancelling a wait does not stop an already running `spawn_blocking` task or application-spawned work. JSON byte and structure budgets do not bound CPU time in user serialization or deserialization implementations. Applications should budget CPU-heavy or blocking work separately; use process isolation when forced termination is required. Applications own cancellation cooperation and business side effects.

The accept loop injects Axum `ConnectInfo<SocketAddr>` into every HTTP and HTTPS request, including every stream on an HTTP/2 connection. It identifies the direct TCP peer, which may be a reverse proxy, and is not a verified user identity. Forwarded headers are not trusted; proxy resolution belongs to application policy.
