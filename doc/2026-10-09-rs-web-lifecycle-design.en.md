# rs-web lifecycle and resource boundary design

> Date: 2026-10-09. This summary describes the current `qubit-web` 0.3.0 contract. For operational steps, see the [English user guide](user_guide.md) and [Chinese user guide](user_guide.zh_CN.md). The [2026-10-08 design record](2026-10-08-rs-web-design.md) is historical and includes superseded API proposals.

## Long-lived request admission

Controller `sse`/`ws` routes and native Axum long-lived routes need bounded request admission before a stream or upgrade starts. Controller routes share a builder-owned `StreamAdmissionState`; native Axum routes install `StreamAdmissionLayer` explicitly, using `StreamAdmissionState`/`from_state` when branches should share capacity. Each state domain defaults to 1 MiB per buffered body, 256 concurrent admissions, and a 10-second deadline through response headers. That is a 256 MiB estimate of concurrent request payloads per domain, not a limit on buffer allocations or process peak memory. Incremental buffering releases each prior data-frame owner after copying; vector growth, temporary coexistence during growth, the current frame, trailers, allocator behavior, and transport buffers remain additional costs. The middleware buffers the complete request before the handler; 413 `body_too_large`, 400 `body_read_failed`, 503 `capacity_exceeded`, and 504 `request_timeout` identify size, read, capacity, and deadline failures. If the absolute deadline cannot be represented at runtime, admission returns HTTP 500 `invalid_configuration`. The deadline does not cover an SSE response body or WebSocket session. This admission budget is separate from short-request `RequestLimitLayer` and from the SSE/WebSocket session policies below.

## Response-body diagnostics

`DiagnosticLayer::new()` keeps its response-header-only behavior. Applications opt in to response-body termination events by installing `DiagnosticLayer::with_body_diagnostics()` outside `RequestLimitLayer`; this lets the observer receive the limit layer's timeout notification even when the transport stops polling. Each request emits at most one `response_body_end` event with outcome `complete`, `timeout`, `body_error`, or `dropped`. The status is the response-header status, and elapsed time ends at the observed terminal state. The event uses allowlisted request metadata and omits body bytes and error text. `dropped` does not establish that the client disconnected, while `complete` does not establish network delivery. A WebSocket upgrade's HTTP response-body completion says nothing about the later WebSocket session; SSE is observed only as an HTTP response body.

## Managed session admission and shutdown

`ServerContext::try_register_session()` atomically reserves a managed session unless shutdown has begun. `active_sessions()` includes managed SSE connections and WebSocket upgrades admitted through `WsUpgradePolicy::on_upgrade`, even while the upgrade response is pending. SSE and WS admission after shutdown begins is rejected. Ordinary HTTP requests, native Axum upgrades, and arbitrary application background tasks are not managed sessions.

SSE and WebSocket capacity limits are separate policy domains, not a total service-wide session cap. Each `SseConnectionPolicy::new`/`default` and `WsUpgradePolicy::new`/`default` creates an independent domain; clones of the same policy share its domain. The default capacity is 128 connections per policy instance. `WsUpgradePolicy` validates final field values: `max_connections` must be within `1..=tokio::sync::Semaphore::MAX_PERMITS`; zero returns `WsPolicyError::ZeroLimit`, and larger values return `WsPolicyError::ConnectionLimitTooLarge`. Invalid policies cannot upgrade. Creating policies separately for different routes therefore adds their capacities. To enforce one shared limit across routes, create a policy once at startup, store it in application state, and use clones from that state. `ServerContext::active_sessions()` is shutdown accounting, not an additional numeric admission limit.

The server stops accepting connections, closes session admission, and notifies active sessions when shutdown starts. It waits for HTTP connection tasks and managed sessions against one absolute deadline. `ShutdownReport::graceful` is true only when both groups actually finish at or before that deadline. The server records transport task completion when each task releases its connection resources and uses the session tracker's deadline snapshot; late task scheduling or delayed report observation does not turn an on-time completion into a timeout, and an `Ok` wait result does not make a late completion graceful. `unfinished_managed_sessions` records the managed session count at the deadline. The report does not claim that arbitrary application work has stopped. `WebServer` owns and tracks the connection tasks, while Hyper/hyper-util drives each connection. This implementation does not provide a provable count of forcibly closed connections, so `forced_connections` is `None`.

The shutdown duration is configured once through `ServerOptions` and carried by `ServerContext`; `WsUpgradePolicy` has no policy-level shutdown timeout. WebSocket reader and writer shutdown use the server's shared absolute deadline.

Dropping or aborting a `serve` future after it has been polled closes managed-session admission and notifies active sessions synchronously. Drop cannot await asynchronous draining or produce a `ShutdownReport`; Tokio must continue scheduling cleanup. Hosts that need graceful draining and a report should resolve the shutdown future and await `serve`. A never-polled `serve` future is outside this cancellation guarantee.

## Transport idle timeout

`ServerOptions::transport_idle_timeout` defaults to 30 seconds and must be nonzero. Configuration uses `transport.idle_timeout_ms`, also defaulting to `30000`. A TCP/TLS transport with no active request handler or response body is closed after this idle interval, including a connection that never sends its first HTTP/2 request. Active handlers and bodies pause the idle timer, so a long-lived SSE response is not closed as idle. HTTP/2 PING frames do not reset request activity. The separate `request_header_timeout` remains 10 seconds for HTTP/1 headers and TLS handshake; an idle timeout does not bound a stalled active request.

## WebSocket queue and inbound delivery

All clones of a WebSocket send queue share its closed state. After the peer or session closes, `try_send` returns `Closed`; a successful enqueue does not guarantee network delivery. `queue_limits` configures the outbound queue. The separate `inbound_queue_limits(messages, bytes)` defaults to 64 queued messages and 1 MiB aggregate payload per connection; the reader may hold one additional pending message, charged to the same byte budget. For 128 active default connections, queued and pending payloads are bounded to about 128 MiB, plus at most one 1 MiB protocol-reassembled message per active connection. This estimate excludes allocation overhead and application-owned memory; it does not bound memory retained by handlers or sessions after their I/O ends. A message too large for the remaining budget is dropped and closes with code `1013` immediately. When only channel slots are unavailable, delivery waits up to `WsUpgradePolicy::idle_timeout`, then closes with code `1013` and reason `inbound backpressure`. `WsSession::recv()` transfers message ownership to the application, outside this queue budget. Applications should keep receiving messages and hand off longer processing after receipt.

An ordinary write stops waiting for its flush when server shutdown is cancelled. After the peer has sent Close, the writer's final flush is bounded by the server's shared close deadline. Under backpressure, a Close frame may not be delivered. When the writer reaches a Close queued by the application, it closes the outbound queue, discards messages behind that frame, preserves its code and reason, and starts the shared close deadline. The peer acknowledgement wait is bounded by that deadline; `try_send` success before the writer reaches Close still means enqueue only. The connection-policy permit and managed-session registration are held by the I/O resources shared by the reader and writer, and are released only after both tasks drop their references. Writer termination alone does not establish that session capacity has been reclaimed.

## Session close and configuration boundaries

`WsSession::close()` is idempotent. If the close future is cancelled while waiting, it can be called again; after explicit closure `recv()` returns `None` and discards a pending read error. A transport read error is stored separately from the bounded channel and can be received once as `Some(Err(_))` after cancellation cleanup; subsequent receives return `None`. If a `recv()` future is cancelled while cleanup is pending, the error remains available for a later receive. Host shutdown may cancel the handler without delivering the error. Queue cleanup drops pending inbound envelopes and releases their byte budget. When the writer exits, it closes the outbound queue, discarding pending messages and releasing their queued-byte budget; a message already in flight remains charged until the writer finishes that send. This queue-budget cleanup is separate from releasing the shared connection-policy permit and managed-session registration, which occurs only after both I/O tasks release their resource references. The HTTP request-header timeout and SSE keep-alive interval reject zero or durations that cannot be represented by `Tokio Instant::checked_add`, including `Duration::MAX`, with `WebServerError::InvalidConfig`.

`WsSession::closed()` returns an owned `Send + 'static` future that can be created before or after I/O termination and awaited by multiple callers. It resolves after both reader and writer release the connection permit and managed-session registration; it does not mean that a Close frame reached the peer, the handler or application work finished, or inbound messages were consumed. Applications can select it against work that is safe to cancel, then call `close()` to drop queued input. The notification does not cancel handlers or spawned work. Applications that must continue work should transfer the required input and manage that work independently.

## Origin and application authentication

`WsUpgradePolicy::new()` permits a request with no Origin to proceed to application authentication. If a request includes Origin, the default policy rejects it; configure `allowed_origins` to accept exact values. Applications remain responsible for authenticating before calling `on_upgrade`. Origin validation is not authentication.

## I/O error boundary and API migration

`WebServerError` retains socket bind, local-address, and accept failures as `io::Error` sources. Callers can inspect `std::error::Error::source()` for diagnostics. Default `Display` and `Debug` output omit the underlying OS error text; TLS and configuration errors do not expose potentially sensitive source chains.

The WebSocket writer emits at most one structured warning per writer lifetime for a failed sink send or control-frame flush, including a real error from the bounded final flush after a peer Close: `event="websocket_io_failure"`, `direction="write"`, and `operation="send"` or `"flush"`. It does not record payloads or the underlying sink error text. A successful peer-close flush is quiet; cancellation and close-confirmation timeout are not reported as write failures. A successful `WsSession::try_send` still means enqueue only, not network delivery.

Historical note — version 0.2.0 introduced these intentional breaking changes: token-only WebSocket upgrades are removed in favor of `WsUpgradePolicy::on_upgrade(ws, headers, context, handler)`, WebSocket shutdown timing is configured only through `ServerOptions` and `ServerContext`, `WebServerError` is no longer a copyable source-free enum, and SSE admission distinguishes capacity exhaustion from shutdown rejection.

## Cooperative cancellation boundary

Deadlines depend on Tokio getting scheduled. Non-yielding synchronous work can delay timeout checks and cleanup and can finish after a deadline. Cancelling the wait does not stop an already running `spawn_blocking` task or application-spawned work. Applications should give CPU-heavy or blocking jobs a separate concurrency budget and use process isolation when forced termination is required. Byte and structure budgets do not bound CPU time in user JSON `Serialize` or `Deserialize` implementations; cancellation cooperation and business side effects remain application responsibilities.
