# rs-web 入门文档与下游当前源码联调设计

> 状态：待实施设计。依据本轮 rs-web 重新评审中用户已接受的两项意见编写；本文不表示 README 或 CI 已改动。实施步骤见[同轮计划](implementation-plan-20261013T160345113Z-029cf798.md)。

## 背景与证据

1. `README.md` 与 `README.zh_CN.md` 的 Quick start／快速开始目前给出 `cargo run --example controller_crud --all-features` 和 `curl` 命令，并描述了 `ServerOptions`、Router、HTTP 限额与 `WebServer::serve` 的关系，但没有在正文展示这些 API 的最小服务端装配代码。读者必须打开 `examples/controller_crud.rs` 才能看到调用链。双语用户指南已有更完整的配置、SSE/WS 和停服专题；README 应让首次接入者在正文走通最小路径，并继续把细节引向指南。
2. `/data/working/qubit/rust-common/rs-websocket/Cargo.toml` 的开发依赖 `qubit-web` 固定在 Git revision `3046fa0fbc46c6c4584fdf9710b45649dfebd70a`。该仓库 `tests/web_interop_tests.rs` 的五个集成用例覆盖握手、Origin、消息、关闭与停服，但在现状下只检验固定 revision，不能证明 rs-web 当前提交与该客户端互通。
3. rs-web 的 `.github/workflows/ci.yml` 目前只调用共享 `rs-infra-ci` 工作流；仓库自身已有完整的 HTTP、HTTPS、JSON、Controller、SSE、WS 测试。上轮评审运行 `cargo fmt --all -- --check` 与 `cargo test --workspace --all-features --all-targets` 均通过。本方案不以重新设计这些已有能力为目标。

## 目标与验收合同

- 中英文 README 正文均包含同一真实任务的最小、完整且可编译的服务端示例：安装依赖、绑定 loopback、建立 Router、只为选定的普通短路由安装 `RequestLimitLayer`、调用 `WebServer::bind_http` 与 `serve`、触发停服，并说明可观察的 HTTP 响应。两版事实、命令、限制一致，中文独立组织表达。
- 示例用公开 API，与仓库当前 `Cargo.toml` 的 Rust 2024、Axum 0.8、`qubit-web` 0.2 和 Tokio 1 相符。`/health` 的成功响应与停服触发都能由正文代码解释；不把现有 CRUD 示例的 `/users` 行为误归给这个最小示例。
- rs-web 的 PR 和 main CI 增加一个当前源码互操作门禁：取得 rs-web 当前 checkout 与 rs-websocket checkout，把下游测试的 `qubit-web` Git 依赖仅在本次 Cargo 调用中覆盖为当前 rs-web 本地路径，运行 `web_interop_tests`，并在测试前证明 Cargo 实际选择的是本地 rs-web package。失败时该 job 失败，不静默退回固定 revision。
- 保留 rs-websocket 仓库现有固定 revision 的测试用途；本方案不改写其 `Cargo.toml`、`Cargo.lock` 或业务测试。当前源码门禁与固定 revision 验证分别回答“本次 rs-web 改动是否兼容下游”和“下游在已锁定版本上是否仍能构建”。
- 不引入 rs-web 公共 API 变更或生产代码重构。用户允许必要的破坏性变更，但上述两项目标没有此需求。

## 方案选择

### README 示例

| 方案 | 取舍 | 决定 |
| --- | --- | --- |
| 仅增加 `examples/controller_crud.rs` 的链接和说明 | 改动最少；仍需跳转并阅读完整 CRUD 才能理解最小接入 | 不采用 |
| 在两版 README 正文展示完整的最小 native Axum 服务，保留 CRUD 与流式示例入口 | 首次接入可直接照做；会有少量与示例文件重叠的基础代码 | **采用** |
| 将完整 CRUD 示例复制到 README | 复制大量业务状态与 JSON 代码，维护成本高 | 不采用 |

最小场景选择 `/health` 与 `/admin/shutdown`：应用创建 `Router`，只在 `/health` 的 `get` 分支安装 `RequestLimitLayer::new(HttpLimits::default())`，使用 `Arc<tokio::sync::Notify>` 让应用自身的停服路由触发 `serve` 的 shutdown future。监听 `127.0.0.1:3000`，示例只用于 loopback 演示。正文 Cargo 片段列出直接使用的 `axum`、`qubit-web`、`tokio` 依赖和 Tokio 所需 feature；正文 Rust 片段给出完整 `main`。`curl` 验证只检查最小示例实际提供的两个端点；现有 `/users` CRUD 验证仍放在完整示例段落并标明来自 `controller_crud`。Controller 短路由默认限额、原生分支显式限额、SSE/WS 不能使用短请求期限这三条合同继续保持准确。

### 下游互操作门禁

| 方案 | 取舍 | 决定 |
| --- | --- | --- |
| 把 rs-websocket 的固定 Git revision 直接改成当前 rs-web path | 本地联调方便，但下游独立检出与固定版本验证受损 | 不采用 |
| 在 rs-web 新增依赖 rs-websocket 的测试 | 造成循环的开发依赖与共享 CI 对兄弟目录的隐含要求 | 不采用 |
| rs-web 增加独立 CI job，检出下游并以 Cargo `patch` 配置覆盖 Git 源 | 仅联调 job 使用当前源码，既有包与下游锁定依赖不变 | **采用** |

新 job 放在 rs-web 的 `.github/workflows/downstream-interop.yml`，由 PR、main push、手动触发。先检出当前 rs-web 到 `rs-web/`，再检出 `qubit-ltd/rs-websocket` 到 `rs-websocket/`，使用仓库固定的 Rust 1.94 toolchain。将同一条 Cargo `--config 'patch."https://github.com/qubit-ltd/rs-web".qubit-web.path="<当前绝对路径>"'` 参数用于 `cargo metadata` 和 `cargo test --manifest-path rs-websocket/Cargo.toml --test web_interop_tests`。实施时必须以实际 Cargo 解析结果确认此 source patch 能覆盖带 `rev` 的 Git 依赖；若不能覆盖，停止该 job 的实施并据实际 Cargo 行为修订覆盖方式，不能退回旧 revision 却声称当前源码已通过。`cargo metadata` 的验证应解析 `packages` 与 `resolve`，确认 `qubit-web` 0.2.0 的 `manifest_path` 指向 job 中 rs-web 的 `Cargo.toml`，而非只靠测试通过推断覆盖生效。当前源码 job 不使用 `--locked`，因为切换依赖来源会改变临时下游解析；临时 checkout 的 lock 差异不回写仓库。

下游默认分支会变化，因此 CI 在日志中打印其 checkout SHA，并对测试结果只宣称“rs-web 当前 SHA 与该次下游 SHA 互通”。若下游 API 未来有意改变，先核对失败来自 rs-web 回归还是下游新需求，再更新此 job 的目标 revision 或适配测试。无需把 GitHub Actions 对外仓库网络故障误报为 rs-web 运行时缺陷，但 job 仍应失败以保留门禁可见性。

## 文件边界与验证

| 路径 | 责任 |
| --- | --- |
| `README.md`、`README.zh_CN.md` | 最小可编译调用链、操作与预期结果；保留现有详细示例和双语导航 |
| `.github/workflows/downstream-interop.yml` | 当前源码下游联调的 checkout、Cargo 解析断言与五个互操作用例 |
| `doc/README.md` | 把本轮设计与实施计划列入历史／实施记录索引，不把待实施方案表述为现行行为 |

实施时先用临时消费者 crate 编译 README 的完整片段，随后运行最小服务并验证 `GET /health` 为 200／`ok`、`POST /admin/shutdown` 为 202，服务进程正常退出。再核对两版安装片段、路由、命令、结果及限制的语义一致性和相对链接。CI job 需先在本地两个仓库检出条件下运行 `cargo metadata` 路径断言与 `web_interop_tests`，然后检查 YAML 触发条件、权限与 checkout 路径。最后运行 rs-web 的格式和全功能测试；若仅文档与 workflow 变化，测试只用于确认基线没有被误改，不据此宣称下游门禁已在 GitHub 运行。

## 风险与范围限制

- README 示例需要直接声明 Axum/Tokio 依赖，不能给人“只添加 `qubit-web` 就能编译”的错觉；shutdown 端点仅绑定 loopback，不能作为生产环境的未授权管理接口模板。
- Cargo patch 的 source URL、路径引号和临时 lock 解析最易出错。实施计划要求先验证 `manifest_path`，再运行互操作测试；覆盖失败必须直接报错。
- 新 job 依赖 GitHub 能检出 rs-websocket 默认分支。测试用例来自该仓库的现有 `tests/web_interop_tests.rs`，不在 rs-web 中复制维护第二套协议测试。
- 本轮不处理未在上次评审确认的其他架构、风格、Rustdoc 或覆盖率议题；不扩大为生产 API 重构。
