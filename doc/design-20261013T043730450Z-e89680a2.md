## 背景与目标

本轮评审确认了两个值得改进的地方：

1. `WsUpgradePolicy` 的 `invalid_limits` 使用累积标记。调用者先传入无效值、再用同一 setter 改成有效值时，`validate()` 仍报错，`on_upgrade()` 因而返回 HTTP 500。现有测试只覆盖单次无效设置。
2. `ControllerRoutes::add` 每次克隆全部既有路由声明并重建 `matchit::Router`。多次添加 Controller 时，重复处理已校验的路由；该成本随累计路由数增长。

目标是让 WebSocket 策略以**最终配置**决定有效性，保留原有连接容量域语义；让 Controller 路由校验只处理本次新增声明，同时保持既有错误分类、注册时机和路由行为。项目继续使用 Rust 2024、最低 Rust 1.94、Axum 0.8、Tokio 1；不增加依赖。允许公共错误枚举发生破坏性变更。

## 方案选择

### WebSocket 校验

| 方案 | 结果 | 取舍 |
| --- | --- | --- |
| 在每个 setter 中清除累积标记 | 同一字段被修正后可能恢复有效 | 多个字段分别出错时容易误清除，仍须维护派生状态。 |
| 将 setter 改为立即返回 `Result` | 无效值立即暴露 | 需要大幅改写链式调用，且不符合现有 `validate()` 合同。 |
| **保留字段原始最终值，在 `validate()` 中逐字段判断** | 修正任一字段后自然重新计算，错误与最终值一致 | `max_connections` 必须把原始请求值与安全的 Semaphore 容量分开处理。选用此方案。 |

### Controller 路由

| 方案 | 结果 | 取舍 |
| --- | --- | --- |
| 继续克隆声明，但缓存匹配器 | 减少一部分重建 | 每次 `add` 仍复制累积状态。 |
| **在 builder 中持久保存匹配器和方法索引，直接增量插入** | 每次只校验本次路由 | 依赖 `add(self) -> Result<Self, _>` 失败时消费 builder 的现有所有权合同。选用此方案。 |
| 一次性收集全部 Controller 后统一装配 | 可以批量校验 | 改动公共 API 和装配顺序，超出需要。 |

## WebSocket 配置合同

`PolicyInner` 移除 `invalid_limits`。`max_connections` 字段保存调用者最后设置的原始值；`connections` 始终指向安全创建的 Semaphore：当值处于 `1..=Semaphore::MAX_PERMITS` 时使用该值，否则创建零容量 Semaphore。这样无效的超大值不会使构造过程 panic，也不会被悄悄截断为有效值。再次调用 `max_connections` 会创建新容量域，原 policy 克隆和已接纳会话继续留在旧域，维持既有语义。

`validate()` 每次读取最终字段，按固定顺序返回首个错误：`max_connections == 0`、frame/message/queue 限额为零或 idle timeout 为零时返回现有 `WsPolicyError::ZeroLimit`；`max_connections > Semaphore::MAX_PERMITS` 时返回新增的 `WsPolicyError::ConnectionLimitTooLarge`。不在错误值中包含实际容量。`on_upgrade()` 对任何无效策略仍返回 HTTP 500；Origin 和容量拒绝的顺序保持不变。

`active_connections()` 对无效 `max_connections` 返回 0；因为无效 policy 无法进入 `on_upgrade` 的接纳阶段，当前域没有已接纳会话。对有效 policy，继续使用 `max_connections - available_permits()`。从已有 policy 克隆后修改非容量字段时，仍共享原容量域；修改容量字段时，按现有合同切换到新容量域。

示例合同：

```rust
assert!(WsUpgradePolicy::new().max_connections(0).max_connections(1).validate().is_ok());
assert!(WsUpgradePolicy::new().max_frame_bytes(0).max_frame_bytes(1).validate().is_ok());
assert_eq!(
    WsUpgradePolicy::new()
        .max_connections(tokio::sync::Semaphore::MAX_PERMITS + 1)
        .validate(),
    Err(WsPolicyError::ConnectionLimitTooLarge),
);
```

同一字段被修正后可恢复有效；其他字段若仍为零，仍须拒绝。`WsPolicyError` 增加枚举变体属于允许的破坏性变更，现有穷尽匹配调用方需要更新。

## ControllerRoutes 增量校验合同

在 `ControllerRoutes<S>` 中增加私有 `matcher: matchit::Router<()>`，并由 `new()` 初始化。`declared` 继续保存完整路径到已声明 HTTP 方法的索引。`add` 对本次 metadata 按顺序执行：

1. 若相同完整路径与方法已声明，返回 `DuplicateMethod`。
2. 若完整路径尚未在 `declared` 中，仅将该路径插入持久 `matcher`；`matchit::InsertError::Conflict` 映射为 `PatternConflict`，其他插入错误映射为 `InvalidPath`。
3. 在 `declared` 中记录方法。不同方法可共用同一路径；同一 Controller 内的后续声明也会看到前面插入的路径与方法。
4. 本次全部 metadata 通过后才调用 `C::register`。

任何校验错误都会消费当前 builder 并返回 `Err`，调用者无法再用部分改动的 builder；因此不需要克隆后回滚。已交给 `Router` 的路由仍只发生在完整 preflight 之后。公共方法签名、错误类型、路由优先级、短请求限额共享方式均保持不变。

若 `ControllerDefinition::route_metadata()` 与 `register()` 不一致，Axum 仍可能在注册时 panic；这属于现有手写实现合同，不在本次变更范围。

## 实施边界与风险

这两个变更可以独立实施；最终统一验证与文档校对。`WsPolicyError` 新变体可能影响穷尽匹配。Controller 匹配器增量插入要求严格保持“相同路径不同方法只插一次”的顺序；测试要覆盖同一 Controller 内和跨 Controller 的重复／冲突。性能收益来自消除对既有声明的每次克隆和重建，不以微基准数字作为验收条件。

不修改 SSE、HTTP 传输、JSON、TLS、宏展开逻辑或下游依赖固定版本；不因本次重构改变公开的 Controller 装配 API。
